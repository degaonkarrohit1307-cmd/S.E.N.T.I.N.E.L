# ADR-0005: v0.3.2 — Plugin Lifecycle Management

**Status:** Accepted
**Date:** 2026-07-25
**Scope:** Lifecycle state machine and hook invocation only. Dynamic
import of plugin code remains a future phase's responsibility.

## Context
v0.3.1 (Phase 1) produced `PluginManifest` objects via discovery, with
no notion of runtime state. v0.3.2 adds the state machine every
discovered plugin moves through, and the mechanism for invoking a
plugin's optional lifecycle hooks as it moves through that machine.

## Why lifecycle management exists
A plugin isn't simply "on" or "off." Between being found on disk and
actively handling events, it passes through distinct, meaningful
states — and several classes of bugs only happen at the *transitions*
between them (starting something twice, stopping something that was
never started, unloading something still running). Centralizing these
rules in one class means every one of these mistakes is caught in
exactly one place, with one consistent error, rather than each caller
having to remember the rules itself.

## State machine

```
DISCOVERED -> LOADED -> INITIALIZED -> RUNNING -> STOPPED -> UNLOADED
                                  \
                                   -> FAILED (from any non-terminal state,
                                               if a lifecycle hook raises)
```

FAILED and UNLOADED are both terminal in this phase: no transition is
defined out of either. A plugin that fails cannot currently be
recovered without external intervention (e.g. re-calling
`register_plugin()`, which resets it to DISCOVERED) — see "Future
extensibility" below for where a dedicated recovery path would go.

## Transition rules

| Action | Required current state | Target state | Hook called |
|---|---|---|---|
| `load_plugin` | DISCOVERED | LOADED | `on_load` |
| `initialize_plugin` | LOADED | INITIALIZED | `on_initialize` |
| `start_plugin` | INITIALIZED | RUNNING | `on_start` |
| `stop_plugin` | RUNNING | STOPPED | `on_stop` |
| `unload_plugin` | STOPPED | UNLOADED | `on_unload` |

Three failure shapes are distinguished, matching the three required
exception types:

1. **Never loaded at all.** If the current state is DISCOVERED and the
   requested action isn't `load` — e.g. calling `unload_plugin()` on a
   plugin that was only ever discovered — this raises
   `PluginNotLoadedError`. The same exception is raised if the plugin
   name was never registered with the manager in the first place; both
   are "this plugin has not been loaded," just for different reasons.
2. **Redoing a transition that already succeeded.** If the current
   state already equals the action's target state — e.g. calling
   `start_plugin()` while already RUNNING — this is the "duplicate
   start" case and raises `PluginAlreadyRunningError` specifically (a
   subclass of `InvalidPluginStateError`) when the target is RUNNING;
   any other repeated transition (e.g. calling `stop_plugin()` twice)
   raises the parent `InvalidPluginStateError`.
3. **Any other wrong-point-in-the-chain transition** (skipping a step,
   going out of order, or acting on a terminal state) raises the
   general-purpose `InvalidPluginStateError`.

`PluginAlreadyRunningError` and `PluginNotLoadedError` both subclass
`InvalidPluginStateError`, so a caller that only wants to catch "any
lifecycle problem" can do so with one `except` clause, while a caller
that cares about the specific reason can catch the subclass.

## Hook invocation and error isolation
Each of the five lifecycle hooks (`on_load`, `on_initialize`,
`on_start`, `on_stop`, `on_unload`) is optional on the plugin instance.
`PluginLifecycleManager` uses `getattr(instance, hook_name, None)` and
only calls it if present and callable — a plugin implementing none, some,
or all of the hooks is handled identically and gracefully, per the
v0.3.2 Plugin API requirement.

If a hook raises, the plugin's state is set to FAILED **before**
re-raising the original exception unmodified. This means:
- the caller sees the real, original exception (no wrapping that would
  obscure the root cause) — verified by
  `test_hook_exception_propagates_to_caller`;
- the manager's internal bookkeeping still correctly reflects that the
  plugin is no longer usable — verified by
  `test_hook_exception_marks_plugin_as_failed` and
  `test_operations_after_failure_raise_invalid_state_error`.

## Design decisions

1. **No dynamic import dependency.** `PluginLifecycleManager` accepts
   an already-constructed instance (or `None`) at `register_plugin()`
   time; it has no opinion about how that instance came to exist. This
   keeps lifecycle management independently testable (as the test suite
   does, entirely with plain Python objects) and keeps dynamic
   import — a materially different, riskier concern involving
   `importlib` and arbitrary code execution — as a clean, separate
   future phase.

2. **Table-driven transitions, not one method body per action.** The
   five actions share one `_transition()` implementation parameterized
   by `_REQUIRED_STATE`, `_TARGET_STATE`, and `_HOOK_NAME` lookup
   tables. Adding a sixth lifecycle stage later means extending three
   dicts, not duplicating a five-branch method.

3. **Re-registration resets to DISCOVERED rather than raising.** A
   plugin manifest may legitimately need to be re-registered (e.g. a
   future reload phase). Rather than requiring a separate
   `reset_plugin()` API now, `register_plugin()` is idempotent and
   logged, keeping the public surface smaller.

## Future extensibility
- **Recovery from FAILED**: a future phase could add a `recover_plugin()`
  transition from FAILED back to DISCOVERED or LOADED, without changing
  any of today's transition rules — the lookup-table design accommodates
  this as a pure addition.
- **Reload**: composing `stop_plugin` + `unload_plugin` +
  `register_plugin` + `load_plugin` + `initialize_plugin` +
  `start_plugin` already yields a full reload with today's API; a
  convenience `reload_plugin()` wrapping that sequence is a natural,
  additive next step.
- **Dynamic import integration**: a future `PluginManager` (distinct
  from `PluginLifecycleManager`, mirroring how `PluginLoader` stayed
  separate from lifecycle in this phase) will use `PluginLoader` to
  discover manifests, dynamically import each entry point, and hand the
  resulting instance to `PluginLifecycleManager.register_plugin()` —
  no changes required to this file.
- **Event Bus / Security integration**: when plugins gain access to a
  `KernelContext` (per the previously approved architecture extending
  it with `subscribe`/`unsubscribe`), that context can be passed into
  `on_initialize()` the same way `Module.on_load()` already receives it
  in the v0.1 Module Registry — again, no change to this file's
  transition logic, only to what the caller passes to the hook.

## Consequences
- No existing file was modified except the additive extension of
  `core/plugin_loader/exceptions.py` (three new exception classes;
  `PluginError` and `PluginManifestError` unchanged).
- New dependency: none. `enum`, `typing`, `logging` are stdlib.
- 25 new tests added (24 lifecycle-specific + 1 closing a coverage gap);
  100% statement coverage on both new modules; 75/75 tests pass overall.
