# ADR-0004: v0.3 Phase 1 — Plugin Discovery

**Status:** Accepted
**Date:** 2026-07-23
**Scope:** Discovery and manifest parsing only. No lifecycle, no dynamic
import, no dependency resolution, no execution.

## Context
v0.3 begins the Plugin Loader system. This phase builds the first,
narrowest slice: find every `manifest.json` under a plugin root and
parse it into a strongly-typed `PluginManifest`.

## Decisions

1. **Recursive discovery via `Path.rglob("manifest.json")`.** A plugin
   author may nest plugins under category subfolders (e.g.
   `modules/integrations/weather/manifest.json`); recursion finds them
   without requiring flat, single-level layout.

2. **A brand-new `PluginManifest`, not a reuse of `ModuleManifest`.**
   The existing `domain/entities/module_manifest.py::ModuleManifest`
   describes a different file (`module.manifest.json`) for a different
   system (the v0.1 Module Registry) with a different schema
   (`required_scopes` vs `permissions`, no `entry_point` since those
   modules are constructed directly by whoever wires them). Reusing one
   class for both would couple two systems that need to evolve
   independently. `SemVer`, being a generic value object with no
   coupling to either schema, **is** reused.

3. **Filename, not location, is what distinguishes the two systems.**
   Both currently live under `modules/`. The Plugin Loader looks
   exclusively for `manifest.json`; the Module Registry looks
   exclusively for `module.manifest.json`. Verified directly:
   `test_discover_against_real_modules_directory_finds_only_weather`
   runs discovery against the actual project `modules/` folder and
   confirms `security_manager` and `demo_echo` are invisible to it,
   while the new `weather/manifest.json` fixture is found.

4. **Invalid manifests are skipped with a logged warning, never raised
   out of `discover()`.** One malformed plugin must not prevent every
   other plugin from being found. `PluginManifest.from_file` still
   raises `PluginManifestError` (so unit tests can assert exact failure
   reasons); `PluginLoader._try_parse` is the one place that catches it
   and converts it into a skip + log line.

5. **`PluginLoader` is stateless.** It holds no notion of "currently
   loaded" or "enabled" plugins — that's deliberately left for a future
   `PluginManager` (Single Responsibility: discovering/parsing manifest
   files is a different concern from tracking runtime lifecycle state).

6. **`plugin_root` is constructor-injected, not hardcoded.** `PluginLoader`
   doesn't know or care that the default root will be `modules/` —
   that decision belongs to whoever constructs it (a future
   `PluginManager`, wired from `ConfigurationManager`'s
   `plugins.directory` key). Keeps this class trivially testable against
   arbitrary `tmp_path` directories, as the test suite does throughout.

## Known limitation (not a blocker for this phase)
Recursive discovery means a plugin's own subdirectory could
theoretically contain a stray `manifest.json` (e.g. a test fixture
nested inside a plugin folder) and be misidentified as a second plugin.
Not addressed here — duplicate-name detection is explicitly a later
phase's responsibility (the "Plugin Validator" work), and this phase's
job is only to parse what it finds, not to arbitrate between multiple
manifests.

## Consequences
- No existing file was modified. Zero regression risk to v0.1/v0.1.1/v0.2.
- New dependency: none. `json` and `pathlib` are stdlib.
- 23 new tests added; all 50 tests (27 prior + 23 new) pass.
