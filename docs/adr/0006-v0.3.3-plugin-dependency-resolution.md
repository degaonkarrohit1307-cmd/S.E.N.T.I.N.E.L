# ADR-0006: v0.3.3 — Plugin Dependency Resolution

**Status:** Accepted
**Date:** 2026-07-25
**Scope:** Dependency graph construction, validation, and topological
load-order computation. Dynamic import and lifecycle remain owned by
their existing, separate modules and are untouched.

## Context
v0.3.1 (discovery) already parses a `dependencies` field on every
`PluginManifest` — it was included in the schema from the start but
never used for anything. v0.3.2 (lifecycle) governs a single plugin's
state transitions but has no concept of *ordering between plugins*. As
soon as a real plugin declares a dependency on another (e.g. `weather`
needing `security_manager` to exist first), something has to compute a
safe load order and reject graphs where that's impossible — that's this
phase.

## Why dependency resolution is required
Loading plugins in directory-scan order (today's `discover()` behavior)
works only by coincidence. A plugin whose `initialize()` hook assumes
another plugin already exists and is running will fail unpredictably
depending on filesystem iteration order. Centralizing "what order is
safe to load in" in one place — rather than leaving each plugin author
to guess or manually sequence things — is the same motivation as
`PluginLifecycleManager` centralizing valid state transitions in
v0.3.2: one class owns the rule, every caller benefits automatically.

## Graph model
`DependencyGraph` is a directed graph: each plugin is a node, each
dependency is an edge from the dependent plugin to the plugin it
depends on. It is deliberately decoupled from `PluginManifest` —
`build_graph()` accepts plain `(name, dependencies)` pairs, not manifest
objects — so the graph data structure can be tested, reasoned about,
and potentially reused (e.g. for the Module Registry's own
`dependencies` field, which already exists but has never been graph-
validated) without taking on the plugin manifest schema as a dependency
of its own.

Two adjacency maps are kept in sync at all times (`_dependencies` and
its mirror `_dependents`), giving O(1) lookups in both directions —
`get_dependencies()` and `get_dependents()` — at the cost of `add_plugin()`
and `remove_plugin()` doing slightly more bookkeeping than a
single-direction adjacency list would require. For a data structure
queried far more often than it's mutated (plugins are added at startup,
queried throughout runtime), this trade-off is the right one.

## Topological sorting (Kahn's Algorithm)
`DependencyResolver._topological_sort()` implements Kahn's Algorithm:

1. Compute each node's in-degree as *the number of dependencies it
   still has* (not the conventional "incoming edges" framing — here,
   in-degree-zero means "has no unresolved dependencies," i.e. is safe
   to load right now).
2. Seed a ready queue with every node at in-degree zero.
3. Repeatedly pop a ready node, append it to the result, and decrement
   the in-degree of everything that depends on it (`get_dependents()`).
   Any dependent that reaches in-degree zero as a result becomes ready.
4. If every node was eventually appended, the result is a valid load
   order. If any remain, they — and only they — are involved in a
   cycle, since a cycle is exactly the condition under which no node
   in it ever reaches in-degree zero.

Both the initial ready-queue seeding and the dependent-processing loop
sort names before appending, making the result **deterministic**
regardless of Python's dict/set iteration order — verified by
`test_resolve_returns_deterministic_order_across_multiple_calls`.

## Cycle detection
Rather than a separate DFS-based cycle-detection pass, cycle detection
falls out of Kahn's Algorithm for free: `len(order) != len(known_names)`
after the algorithm terminates means some nodes were never reached, and
those unreached nodes are exactly the ones participating in (or
downstream of) a cycle. The error message names only those nodes, not
every plugin in the batch — verified by
`test_circular_dependency_error_names_only_the_cycle_not_unrelated_nodes` —
so a large plugin set with one small cycle doesn't produce a
confusing, unrelated-looking error.

## Validation order and exception hierarchy
`resolve()` validates in a specific, deliberate order, each stage
catching a class of problem the next stage would either mask or report
confusingly:

1. **Duplicate plugin names** (`DuplicatePluginError`) — checked first,
   before the graph is even built, since a duplicate name would corrupt
   the graph itself (which node does "weather" refer to?).
2. **Malformed dependency entries** (`InvalidDependencyError`) — self-
   dependency and blank/non-string entries — checked before missing-
   dependency validation, since a self-dependency is a different, more
   specific problem than "the target doesn't exist" even though a
   naive check might otherwise report it as "weather depends on unknown
   plugin 'weather'," which is a confusing and misleading message.
3. **Missing dependencies** (`MissingDependencyError`) — checked after
   the graph is built, using `DependencyGraph.nodes()` (only ever
   explicitly-added plugins) versus the union of every declared
   dependency target.
4. **Cycles** (`CircularDependencyError`) — necessarily last, since
   topological sort only produces a meaningful result once every
   dependency target is known to exist.

All four subclass a new shared `PluginDependencyError` base (mirroring
`InvalidPluginStateError`'s role in v0.3.2), so a caller wanting to
handle "any invalid dependency graph" can do so with one `except`
clause — verified by `test_all_dependency_errors_are_plugin_dependency_errors`.

**Duplicate *dependency entries* within one manifest** (e.g.
`["security_manager", "security_manager"]`) is explicitly **not**
treated as an error — `DependencyGraph.add_plugin()` stores dependencies
in a `set`, silently deduplicating. This is a deliberate distinction
from `DuplicatePluginError`, which is about two different *plugins*
colliding on identity, not one plugin repeating itself — verified by
`test_duplicate_dependency_entry_within_one_manifest_is_harmless`.

## Loading algorithm / PluginLoader integration
`PluginLoader` gains exactly one new method, `discover_in_dependency_order()`,
which calls the existing (unchanged) `discover()`, feeds the result
through a fresh `DependencyResolver`, and returns the manifests
reordered to match the resolved load order. `discover()` itself is not
touched: it keeps its original path-sorted order and its original
tolerant behavior (skip one bad manifest, keep scanning) — a
dependency-graph problem, unlike a single malformed manifest, spans
multiple plugins at once and genuinely cannot be silently
partially resolved, so `discover_in_dependency_order()` lets
`DependencyResolver`'s exceptions propagate rather than swallowing them.
This split is verified directly by
`test_discover_method_itself_is_unaffected_by_v0_3_3_changes`.

## Design decisions
1. **`DependencyGraph` knows nothing about `PluginManifest`.** Keeps
   the graph reusable and independently testable; `DependencyResolver`
   is the one piece of code translating manifests into the graph's
   generic shape.
2. **`DependencyResolver`'s `graph` constructor parameter is injected**
   (Dependency Injection), defaulting to a fresh `DependencyGraph` if
   not supplied, consistent with `PluginLifecycleManager`'s
   constructor pattern from v0.3.2.
3. **No change to `PluginLifecycleManager` or its state machine.**
   Dependency order determines *which plugin gets `load_plugin()`
   called on it first*; it says nothing about lifecycle states
   themselves, so v0.3.2 required zero modification — confirmed by the
   full v0.3.2 test suite passing unchanged.
4. **No change to `PluginManifest` or its `dependencies` field.** It
   was already present, already optional, already defaulted to an
   empty tuple, and already validated as "must be a list" back in
   v0.3.1 — this phase is the first to actually *use* that field.

## Future extension points
- **Optional dependencies**: a manifest field like
  `"optional_dependencies"` could add edges that participate in
  ordering when present but don't trigger `MissingDependencyError` when
  absent — a straightforward addition to `_check_missing_dependencies`
  and `DependencyGraph.add_plugin`'s edge semantics, not a redesign.
- **Version-constrained dependencies** (e.g. `"security_manager>=1.2.0"`)
  would extend `PluginDependency` (currently a plain name-to-name edge)
  with a version constraint field, checked against the target's
  `PluginManifest.version` during `_check_missing_dependencies`.
- **Cross-system dependencies**: a plugin depending on a v0.1 Module
  Registry module (rather than another plugin) is not yet supported —
  `DependencyGraph`'s manifest-agnostic design means this would only
  require a translation layer feeding both manifest types' names into
  the same graph, not a new graph implementation.
- **`PluginManager` integration** (still not built): the future manager
  that ties `PluginLoader`, `DependencyResolver`, and
  `PluginLifecycleManager` together will call
  `discover_in_dependency_order()` once at startup and then drive
  `register_plugin()` / `load_plugin()` / ... across the resolved list
  in order — no changes required to any of the three classes involved.

## Consequences
- No existing file's *behavior* changed. `plugin_loader.py`'s only
  modification is a new method plus an updated module docstring;
  `exceptions.py`'s only modification is four new exception classes
  appended after the existing ones.
- New dependency: none. `collections.deque` is stdlib.
- 35 new tests added (34 dependency-resolution tests + 1 coverage-gap
  closure); 99% statement coverage on the three new modules combined;
  110/110 tests pass overall.
